# Monitor de Reservatório IoT

Sistema de monitoramento remoto do nível de um reservatório de água desenvolvido para a disciplina de Arquitetura de Computadores. O projeto integra simulação de hardware (ESP32 e sensor ultrassônico HC-SR04 no Wokwi), API REST em Supabase Edge Functions, banco de dados PostgreSQL e painel web.

---

## Visão Geral

O sistema simula o acompanhamento contínuo de um reservatório com `400 cm` de profundidade. A partir da leitura de distância entre o sensor e a superfície da água, o microcontrolador calcula o volume percentual (`0%` a `100%`) e envia os dados periodicamente via HTTPS. Quando o nível fica abaixo de `20%`, um alerta é disparado tanto no circuito simulado (LED) quanto na API e no painel web.

### Especificações de Funcionamento

* **Variável monitorada:** Nível do reservatório (`%`) e distância medida (`cm`).
* **Período de amostragem:** `10 segundos` (`10000 ms`).
* **Filtragem no dispositivo:** Média aritmética de 5 leituras consecutivas, descartando medições fora da faixa válida (`< 2 cm` ou `> 450 cm`).
* **Condição de alerta:** Nível inferior a `20%`.
* **Detecção de falha de comunicação:** O painel sinaliza dados desatualizados se nenhuma leitura nova for registrada em `30 segundos`.
* **Controle remoto:** O painel permite alternar entre o modo automático (leitura real do sensor) e o modo manual (simulação de nível definida pelo usuário).

## Arquitetura da Solução

A comunicação entre os blocos segue o fluxo de envio direto por HTTPS:

```text
[ESP32 + HC-SR04 (Wokwi)]
          │
          ▼  HTTPS (POST / e GET /command)
[API REST — Supabase Edge Function]
          │
          ▼  SQL (Service Role)
[PostgreSQL — Supabase]
          │
          ▼  HTTPS (GET /latest, /history, /command)
[Painel Web — HTML/CSS/JS]
```

### Relação com Arquitetura de Computadores

* **Camada embarcada (ESP32):** Gerencia os pinos de I/O digital para disparo do pulso ultrassônico (`TRIG`) e leitura de largura de pulso (`ECHO`), aplica o filtro de média em memória antes da transmissão e estabelece conexão segura TLS/HTTPS sobre Wi-Fi.
* **Camada de serviço (Edge Function):** Funciona de forma stateless, validando a origem das requisições por cabeçalho de autenticação (`x-device-token`), aplicando a regra de alerta e isolando o banco de dados do acesso público.
* **Persistência (PostgreSQL):** Mantém o histórico temporal das leituras independentemente de o painel estar aberto ou fechado.
* **Interface (Frontend):** Realiza polling a cada `5 segundos` na API, calcula métricas estatísticas (mínimo, máximo, média e tendência linear) e identifica intervalos sem transmissão.

## Estrutura do Banco de Dados

O banco no Supabase utiliza duas tabelas no schema `public`:

### `readings` — Registro de medições

```sql
create table if not exists public.readings (
  id          bigint generated by default as identity primary key,
  device_id   text not null,
  quantity    text not null,
  value       double precision not null,
  unit        text not null,
  distance_cm double precision,
  alert       boolean not null default false,
  source      text not null default 'sensor',
  created_at  timestamptz not null default now()
);
```

### `control` — Estado do controle remoto

```sql
create table if not exists public.control (
  id         int primary key,
  manual     boolean not null default false,
  level      double precision not null default 50,
  updated_at timestamptz default now()
);

insert into public.control (id) values (1) on conflict do nothing;
alter table public.control enable row level security;
```

## Rotas da API REST

| Método | Endpoint | Autenticação | Função |
| :--- | :--- | :--- | :--- |
| `POST` | `/` | Header `x-device-token` | Valida e grava uma nova leitura enviada pelo ESP32. |
| `GET` | `/latest` | Pública | Retorna a última leitura registrada no banco. |
| `GET` | `/history?limit=50` | Pública | Retorna o histórico recente de medições (máximo de 500 registros). |
| `GET` | `/command` | Pública | Consulta o modo de operação atual (`manual` e `level`). |
| `POST` | `/command` | Header `x-panel-pin` *(opcional)* | Atualiza o modo de operação ou nível manual pelo painel. |

## Como Executar o Projeto

### 1. Banco de Dados e API (Supabase)

1. Crie um projeto no Supabase e execute os scripts SQL da seção anterior (ou o arquivo `supabase/atualizar_banco.sql`) no **SQL Editor**.
2. Faça o deploy da Edge Function utilizando o código de `supabase/functions/smooth-action/index.ts`.
3. Configure as variáveis de ambiente (**Secrets**) no painel da função sem versionar chaves no repositório:
   * `SUPABASE_URL` — URL do projeto no Supabase
   * `SUPABASE_SERVICE_ROLE_KEY` — Chave de serviço para escrita no banco
   * `INGEST_TOKEN` — Token de autenticação utilizado pelo ESP32
   * `PANEL_PIN` — *(Opcional)* PIN para restringir alterações no controle remoto

### 2. Simulação (Wokwi)

1. Acesse a simulação pelo link do Wokwi ou importe os arquivos `wokwi/diagram.json` e `wokwi/sketch.ino`.
2. Ajuste as constantes de conexão no topo do arquivo `sketch.ino`:
   ```cpp
   const char* API_URL      = "https://<SEU-PROJETO>.supabase.co/functions/v1/smooth-action";
   const char* DEVICE_TOKEN = "<SEU_INGEST_TOKEN>";
   ```
3. Inicie a simulação. Clique no sensor **HC-SR04** para alterar a distância simulada e utilize o **botão verde** para pausar ou retomar o envio de pacotes.

### 3. Painel Web

1. Verifique se a constante `API` em `dashboard/index.html` corresponde à URL da sua Edge Function.
2. Abra o arquivo `index.html` diretamente no navegador ou hospede a pasta `dashboard/` em um serviço estático (como Cloudflare Pages ou GitHub Pages).
